# ado-ee

Automation Development Office (ADO) Ansible Execution Environment.

This repository defines and builds a container image that packages Ansible, system/Python dependencies, and the `infra.ado` collection so playbooks run the same way in AAP, CI, and local development.

Published images are available from GitHub Container Registry:

```text
ghcr.io/automation-development-office/ado-ee:<tag>
```

## How it works

1. **Definition** — `execution-environment.yml` tells [ansible-builder](https://docs.ansible.com/projects/builder/) what base image and dependencies to use.
2. **Dependencies** — Galaxy collections (`requirements.yml`), Python packages (`requirements.txt`), and system packages (`bindep.txt`) are installed into the image.
3. **Build** — `ansible-builder` generates a build context (`Containerfile`/`Dockerfile`) and builds the image with Podman or Docker.
4. **Test in CI** — On push/PR changes to EE files, [`.github/workflows/test-ee.yml`](.github/workflows/test-ee.yml) builds the image locally in Actions, verifies `infra.ado` is present, and posts a summary (no GHCR publish).
5. **Publish** — On a GitHub Release, [`.github/workflows/build-ee.yml`](.github/workflows/build-ee.yml) builds the EE, pushes it to GHCR, and attaches a compressed image archive to the release.

### Base image

```text
registry.redhat.io/ansible-automation-platform-26/ee-supported-rhel9:latest
```

That image includes Ansible Core, Ansible Runner, and Red Hat–supported collections. This project adds ADO-specific content on top (notably `infra.ado`).

### Layout

| Path | Purpose |
| --- | --- |
| `execution-environment.yml` | ansible-builder definition (schema v3) |
| `requirements.yml` | Ansible collections/roles to install |
| `requirements.txt` | Extra Python packages |
| `bindep.txt` | Extra system (RPM) packages |
| `files/ansible.cfg` | Ansible config copied into the image |
| `.github/workflows/test-ee.yml` | CI test build + EE report (no publish) |
| `.github/workflows/build-ee.yml` | Release build, GHCR publish, release asset |

The `context/` directory is generated by ansible-builder and is gitignored — do not commit it.

## Prerequisites (local)

- [Podman](https://podman.io/) or Docker
- Python 3 with `pip`
- [ansible-builder](https://pypi.org/project/ansible-builder/) 3.x
- Access to `registry.redhat.io` (Red Hat account / registry service account)

Install ansible-builder:

```bash
python3 -m pip install --user ansible-builder
```

Log in to the Red Hat registry (required to pull the AAP base image):

```bash
podman login registry.redhat.io
# or: docker login registry.redhat.io
```

## Test locally before pushing

From the repository root:

```bash
# 1. Generate the build context and build the image
#    Hub token is passed as a build secret (not a build-arg).
printf '%s' "$AUTOMATION_HUB_TOKEN" > .automation-hub-token
ansible-builder build \
  -f execution-environment.yml \
  -t ado-ee:local \
  --container-runtime podman \
  --extra-build-cli-args="--secret id=automation_hub_token,src=$PWD/.automation-hub-token"

# 2. Confirm the ADO collection is present
podman run --rm ado-ee:local ansible-galaxy collection list

# 3. Smoke-check Ansible inside the EE
podman run --rm ado-ee:local ansible --version
```

You should see `infra.ado` and the pinned Hub/Galaxy collections (for example `ansible.controller` 4.6.19, `infra.aap_configuration` 3.4.1) in the collection list.

### Useful local checks

```bash
# Only create the build context (no image build) — useful for reviewing the Containerfile
ansible-builder create -f execution-environment.yml -v 3

# Rebuild without cache if something looks stale
ansible-builder build \
  -f execution-environment.yml \
  -t ado-ee:local \
  --container-runtime podman \
  --extra-build-cli-args="--secret id=automation_hub_token,src=$PWD/.automation-hub-token" \
  --no-cache
```

If the build fails pulling the base image, confirm you are logged into `registry.redhat.io` and that your account can access Ansible Automation Platform images.

If Galaxy install fails for certified/validated collections, confirm `AUTOMATION_HUB_TOKEN` is set and passed via the `automation_hub_token` build secret (see commands above). Create a token at [console.redhat.com Automation Hub](https://console.redhat.com/ansible/automation-hub/token).

## Customizing the EE

| Change | Edit |
| --- | --- |
| Add/update collections | `requirements.yml` |
| Add Python libraries | `requirements.txt` |
| Add OS packages | `bindep.txt` |
| Change base image or build steps | `execution-environment.yml` |

After changes, re-run the local build steps above before opening a PR or cutting a release.

## CI / publishing

### Test build (no publish)

[`.github/workflows/test-ee.yml`](.github/workflows/test-ee.yml) runs on:

- Every pull request
- Every push to `main`
- Manual **workflow_dispatch**

It builds the EE in GitHub Actions, verifies required collections/versions (including `infra.ado` and Hub/Galaxy pins), and writes a job summary with image size, Ansible versions, and the full collection list. The image is **not** pushed to GHCR. A report artifact (`ee-test-report`) is uploaded for download.

#### Required for merge

The `test-build` job is intended as a **required status check** on `main` so PRs cannot merge until it passes.

Apply (or refresh) the GitHub ruleset with:

```bash
# Requires repo admin + authenticated gh CLI
gh auth login   # if needed
./scripts/configure-branch-protection.sh
```

Or set it in the UI: **Settings → Rules → Rulesets →** require status check `test-build` on `main`.

### Release publish

[`.github/workflows/build-ee.yml`](.github/workflows/build-ee.yml) runs when you **publish a GitHub Release** (and can be re-run via **workflow_dispatch** with an existing tag).

It will:

1. Build the EE with ansible-builder + Docker Buildx
2. Push to `ghcr.io/automation-development-office/ado-ee:<tag>` and `:latest`
3. Attach `ado-ee-<tag>.tar.gz` to the release

### Required repository secrets

| Secret | Purpose |
| --- | --- |
| `RH_REGISTRY_USERNAME` | Red Hat registry username / service account |
| `RH_REGISTRY_TOKEN` | Red Hat registry token |
| `AUTOMATION_HUB_TOKEN` | Offline token for console.redhat.com Automation Hub (certified + validated content) |

Create a registry service account at [access.redhat.com/terms-based-registry](https://access.redhat.com/terms-based-registry) if you do not already have one. Create an Automation Hub token at [console.redhat.com/ansible/automation-hub/token](https://console.redhat.com/ansible/automation-hub/token).

Also ensure the repository Actions setting allows **Read and write** permissions so the workflow can publish packages and upload release assets.

### Pull a published image

```bash
podman pull ghcr.io/automation-development-office/ado-ee:v1.0.0
# or
docker pull ghcr.io/automation-development-office/ado-ee:v1.0.0
```

If the package is private, authenticate to `ghcr.io` first (for example with a GitHub PAT that has `read:packages`).
